Taking a lung nodule program live at a US health system: a go-live kit

How I would run a US site deployment for Qure.ai's lung cancer solution, from IT approvals to stabilization, plus tested instructions for the AI agent that turns radiology reports into follow-up tasks.

Built for: Product Manager, US Lung Cancer Solution, Qure.ai (Bengaluru) Inside: phase plan · IT and integration checklist · risk register · agent instructions + 18 tests · SQL · buyer narratives Jump to the agent tester

Independent work. Not affiliated with Qure.ai, and no internal information was used. Product facts come from Qure.ai's public pages. The two hospitals, their rules and all radiology report snippets are fictional, written by me for testing. Nothing here is clinical advice: the agent never decides care, it only routes what the radiologist wrote.

The problem

Qure.ai's own US content cites that 30 to 50% of patients with incidental lung nodules never get the recommended follow-up. Detection alone doesn't fix that. A site only gets value once follow-up actually happens.

The job

Get each US site from signed contract to a stable program fast: IT approvals, DICOM and HL7 flowing, navigators using the worklist, and agents behaving the way that site needs.

The kit

A phase plan with exit criteria, the checklists that usually stall, a risk register, site-specific agent instructions with a working tester, and the SQL I'd watch every morning.

2. The checklist items that usually stall a go-live

IT approvals

  • Security review: have the security questionnaire answers, architecture diagram and certifications (HIPAA, SOC 2 or ISO if held) ready before the first call. Waiting to be asked costs weeks.
  • BAA: start it in parallel with the security review, not after it. Legal queues are the slowest part.
  • Data flow diagram: one page showing exactly which PHI leaves the building, where it goes, and how long it stays.
  • Network: decide on-site gateway versus cloud routing early; firewall change requests often have their own approval cycle.

Integration readiness

  • DICOM routing rules: list every study description the site uses for chest X-rays and chest CTs. Portable AP X-rays and CT abdomen studies that show the lung bases are the easiest to miss.
  • Results back to PACS: confirm how the AI output shows up (secondary capture or structured report) and test it on the radiologists' actual viewing stations.
  • HL7 feeds: the agent needs the final report text. Confirm addenda come through too, because an addendum can change the recommendation (test B1 below).
  • Volume reconciliation: compare studies ordered in the RIS with studies Qure received, every day, per study type. This is the first metric I would watch (SQL query 1).

5. Stabilization: what I'd check every morning




MetricWhy it matters



Capture rate (studies received / studies ordered, by study type)If studies don't arrive, nothing else matters. Catches routing gaps early.


Result delivery and p90 turnaroundA result that lands after the radiologist has signed the report is wasted.


Discordance queue (AI flag, report silent) and review timeThis is where missed nodules get caught, or where alert fatigue starts.


Navigator override rate on agent tasksIf navigators keep editing tasks, the agent instructions are wrong for this site.


Overdue follow-upsThe outcome the customer is buying: fewer patients lost to follow-up.





1. Capture rate: are we receiving every study we should?

SELECT o.study_date,
       o.study_type,
       COUNT(*)                                          AS ordered,
       COUNT(r.accession_no)                             AS received,
       ROUND(100.0 * COUNT(r.accession_no) / COUNT(*), 1) AS capture_pct
FROM ris_orders o
LEFT JOIN qure_received r
       ON r.accession_no = o.accession_no
WHERE o.site_id = 'SITE_A'
  AND o.study_date >= CURRENT_DATE - 14
GROUP BY o.study_date, o.study_type
ORDER BY o.study_date, capture_pct;



2. Turnaround: are results reaching PACS in time?

SELECT site_id,
       DATE(received_at) AS day,
       COUNT(*)          AS studies,
       PERCENTILE_CONT(0.9) WITHIN GROUP (
         ORDER BY EXTRACT(EPOCH FROM (delivered_at - received_at)) / 60
       )                 AS p90_minutes,
       SUM(CASE WHEN delivered_at IS NULL THEN 1 ELSE 0 END) AS not_delivered
FROM qure_received
WHERE received_at >= CURRENT_DATE - 14
GROUP BY site_id, DATE(received_at)
ORDER BY day;



3. Discordance: AI flags the report doesn't mention

SELECT site_id,
       DATE_TRUNC('week', report_final_at)                          AS week,
       SUM(CASE WHEN ai_flag AND NOT report_mentions_nodule THEN 1 ELSE 0 END) AS discordant,
       ROUND(100.0 * AVG(CASE WHEN ai_flag AND NOT report_mentions_nodule THEN 1 ELSE 0 END), 2) AS discordant_pct,
       SUM(CASE WHEN ai_flag AND NOT report_mentions_nodule AND reviewed_at IS NULL THEN 1 ELSE 0 END) AS awaiting_review
FROM findings
GROUP BY site_id, DATE_TRUNC('week', report_final_at)
ORDER BY week;



4. Are navigators trusting the agent's tasks?

SELECT site_id,
       agent_action,
       COUNT(*)                                                   AS tasks,
       ROUND(100.0 * AVG(CASE WHEN navigator_action = 'accepted' THEN 1 ELSE 0 END), 1) AS accepted_pct,
       ROUND(100.0 * AVG(CASE WHEN navigator_action = 'edited'   THEN 1 ELSE 0 END), 1) AS edited_pct,
       ROUND(100.0 * AVG(CASE WHEN navigator_action = 'rejected' THEN 1 ELSE 0 END), 1) AS rejected_pct
FROM agent_tasks
WHERE created_at >= CURRENT_DATE - 28
  AND navigator_action IS NOT NULL
GROUP BY site_id, agent_action
ORDER BY rejected_pct DESC;



5. Overdue follow-ups, by navigator

SELECT site_id,
       assigned_navigator,
       COUNT(*)                                          AS open_followups,
       SUM(CASE WHEN due_date < CURRENT_DATE THEN 1 ELSE 0 END) AS overdue,
       MAX(CURRENT_DATE - due_date)                      AS oldest_overdue_days
FROM followups
WHERE completed_at IS NULL
GROUP BY site_id, assigned_navigator
ORDER BY overdue DESC;
